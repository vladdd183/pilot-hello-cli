## 3. Recommended packaging (PEP 621 + console script)

**Console script table** — PyPA guide, “Creating executable scripts”:

> To install a command as part of your package, declare it in the `[project.scripts]` table.
>
> ```
> [project.scripts]
> spam-cli = "spam:main_cli"
> ```
>
> In this example, after installing your project, a `spam-cli` command will be available. Executing this command will do the equivalent of `import sys; from spam import main_cli; sys.exit(main_cli())`.

URL: https://packaging.python.org/en/latest/guides/writing-pyproject-toml/#creating-executable-scripts

**Mapping to this project:**

| Piece | Recommendation |
|-------|----------------|
| Script name | `hello` (matches intent and acceptance) |
| Entry target | e.g. `hello_cli.cli:main` or `hello.cli:main` — module path + callable |
| Build backend | `setuptools.build_meta` or `hatchling.build` (PEP 517); setuptools is widely documented in the same guide |
| Layout | Flat package `hello_cli/` or `src/hello_cli/` (either valid; keep import path aligned with `[project.scripts]` target) |
| Dev deps | `[project.optional-dependencies] dev = ["pytest"]` so CI can `pip install -e ".[dev]"` (matches planned CI in `research/2.md`) |

**Minimal `pyproject.toml` sketch (conceptual):**

```toml
[build-system]
requires = ["setuptools>=61"]
build-backend = "setuptools.build_meta"

[project]
name = "pilot-hello-cli"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = []

[project.optional-dependencies]
dev = ["pytest>=8"]

[project.scripts]
hello = "hello_cli.cli:main"
```

After `pip install -e ".[dev]"`, the `hello` executable on `PATH` invokes `main()` and should exit with `sys.exit(main())` or return an int from `main` per setuptools convention (PyPA quote above).

## 4. CLI implementation: argparse vs click

| Criterion | `argparse` (stdlib) | `click` |
|-----------|---------------------|---------|
| Dependencies | None | Extra package (often under `[dev]` or runtime) |
| `--help` | Automatic when `add_help=True` (default) | Built-in |
| Fit for one optional flag | Strong | Strong but heavier |

**Recommendation:** **`argparse`** for core — intent asks for a *small* CLI; no dependency on Click is stated. Hints in `questions.yaml` list both; PyPA’s optional-dependencies example mentions `click` only as an illustration, not a requirement.

**`--help`:** Python docs — `ArgumentParser` “automatically generates help and usage messages” and “adds an option which simply displays the parser’s help message” when `-h` or `--help` is supplied (`add_help=True` by default).

URL: https://docs.python.org/3/library/argparse.html

**Suggested interface (conceptual):**

```python
parser.add_argument("--name", default="World", help="Name to greet")
```

Optional bracket in intent `hello [--name NAME]` matches an optional flag with a **default**, not `required=True`.

## 5. Exact greeting string and stdout when `--name` is omitted

**When `--name X` is given:** stdout body must be exactly `Hello, X!` (acceptance). Implementation: `print(f"Hello, {name}!")` or equivalent formatting with no extra spaces.

**When `--name` is omitted:** acceptance and judge do **not** define output; intent only marks `NAME` as optional.

| Option | stdout (body) | Notes |
|--------|----------------|-------|
| **A. `default="World"`** (recommended) | `Hello, World!` | Matches common “hello world” CLI convention; consistent with optional `--name` |
| B. `required=True` | (no greeting; argparse error on stderr, exit 2) | Stricter; contradicts optional `[--name NAME]` UX unless documented |
| C. `default=""` | `Hello, !` | Odd; avoid |

**Research conclusion:** implementers should use **default name `World`** and document it in `--help` unless `delta.md` / architect locks otherwise. The **mandatory** contract remains: `hello --name X` → `Hello, X!`.

## 6. Trailing newline

Python `print()` writes the value plus **`end='\n'`** by default (one newline after the greeting). So typical stdout bytes for `hello --name X`:

```text
Hello, X!\n
```

**Why it matters:** subprocess-based tests (`subprocess.run(..., capture_output=True, text=True)`) and `capsys` often expect the trailing `\n`. A judge that compares raw stdout usually includes that newline unless it strips whitespace. **Recommendation:** use plain `print(...)` (do not use `end=""`) unless acceptance later forbids newline.

Reference: https://docs.python.org/3/library/functions.html#print — “All arguments are converted to strings … and written to the stream, separated by sep and followed by end. The default is a space and `\n` respectively.”

## 7. One unit test (pytest)

**Scope:** one test file, one test function covering the greeting with an explicit name (acceptance).

**Patterns:**

1. **Subprocess (integration, matches real `hello` script):** after editable install in CI, `subprocess.run(["hello", "--name", "X"], check=True, capture_output=True, text=True)` and `assert result.stdout == "Hello, X!\n"` (or `.strip()` only if project standard chooses strip — prefer full stdout match with newline for `print()`).

2. **Import + `capsys` (unit, no entry point):** call `main(["--name", "X"])` with argv injected; `capsys.readouterr().out == "Hello, X!\n"`.

Pytest docs: https://docs.pytest.org/en/stable/how-to/capture-stdout-stderr.html

**Optional second assertion:** `hello --name World` or bare `hello` if default is World — not required by acceptance but documents omission behavior.
